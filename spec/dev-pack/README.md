# CanDo HRIS — Developer Pack

Everything a developer, or an AI coding agent, needs to build CanDo HRIS: what to build (functional requirements), how to build it (architecture, data model, integration and payroll design), the exact data (Canadian statutory rules for 2026 and the National Occupational Classification), proof (a reference payroll calculator with tests checked against CRA), and the order to build in (a step-by-step plan with prompts).

Version: October 2026. Owner: Wael Hussein.

Platform: Supabase (database, authentication, file storage) in `ca-central-1`, Cloudflare Workers (API, jobs, live updates), GitHub (code, reviews, CI/CD), and a small AWS footprint for encryption keys, write-once audit anchors and the recovery backup. Built with Cursor and other AI coding agents through GitHub pull requests.

## How the integration requirements are met

- **Org chart ↔ employee data:** `docs/04`. The chart is a live view of the same effective-dated records as the employee profile. Moving a box creates a change set, and editing a profile creates a change set. Both use one write path, so they can never disagree. Moves can be future-dated, past-dated (with retro pay) or modelled in a plan first.
- **Payroll for any person, day or period:** `docs/06`. A pay run is any population, any work period and any pay date. Every work day is priced with the data in force that day, and deductions follow CRA's pay-date rule. Runs work across fiscal years (GL split by fiscal period) and across calendar years (pay-date year decides tax and T4).
- **Large unionized employers and people with several jobs:** `docs/17`. Tenant-defined org levels (department, cluster, section, sector and others) in several hierarchies; several supervisors with typed relationships; several assignments per person, each with its own rates, agreement, funders and end date; every pay line distributed to funders to the cent; GL by work period and posting period with any fiscal calendar; payroll that starts in the middle of a fiscal year.
- **Benchmarking, job evaluation and total rewards:** `docs/19`. Career levels and families that map to any survey; a competency framework shared by hiring, performance, learning and succession; gender-neutral point-factor evaluation that uses NOC, requirements and competency targets as evidence; any licensed salary survey imported with its masking respected, plus free public wages by NOC; market pricing with lineage; market lines, grades, ranges and posting ranges; a benefits and practice scorecard read from the plans and policies themselves; survey submissions with pseudonyms.
- **People in several positions:** `docs/20`. A position can have two managers, each approving the days, hours or places they supervise (or both, or either); a request is split to the minute across positions and managers, and can be partly approved; nobody approves their own request from another position. Each position carries its own rates, allowances and duty pay, its own review section and competency assessments. Benefits follow each union's plans with coordination, and when one position ends the organization's rules or HR decide what happens, never below the statutory floor.
- **Positions classified any way the employer needs:** `docs/18`. NOC 2021 with every occupation's duties and requirements; any internal or foreign scheme in any order; several codes per position or per incumbent (salary surveys, departments, unique control numbers, legacy IDs), inherited from job to position to incumbent; requirements proposed from NOC and decided by HR; a similar-position search that explains itself; NOC 2026 loaded and recoded when Statistics Canada releases it.

## Design hardening (October 2026)

Four guarantees were added after review:

- **Tamper-evident audit** (`docs/10` §5): every audit row is hashed on insert; an hourly job seals rows into signed Merkle batches anchored in write-once storage in a separate AWS account, and the customer receives a daily copy. An auditor can verify any record without trusting CanDo.
- **Parallel pay runs that cannot double-count** (`docs/06` §9): calculation is split by pay subject (person + payroll account), one open run per subject, YTD written only at finalization. Splitting across 1 or 100 Queue consumers gives the same results to the cent.
- **Frozen inputs and rules** (`docs/06` §8): a locked run reads data as it was known at the lock and rules by content hash; rule editions and agreement versions cannot be changed once tested; a nightly job replays finalized results.
- **Explicit pay composition** (`docs/08` §5): every combination of overtime, holiday and premium has a cited answer in the agreement data, or the agreement cannot be activated.

Platform guards for Supabase and Cloudflare (`docs/02`, `docs/10`, AGENTS rules 23 to 30): business data only through the CanDo API (Supabase's Data API is not used for it), the `service_role` key only in the identity Worker, Hyperdrive caching off, no personal data in R2, KV, Queues or Durable Objects, documents in Supabase Storage in Canada, migrations only from GitHub Actions. A CI script checks these on every pull request.

## How to use this pack with Cursor, AI agents and GitHub

1. Create an empty private GitHub repository, put this whole folder in it, and protect `main` (pull requests only, CI green, one approval, code-owner review). Unzip `CanDo-NOC-2021-data.zip` into `rules/classifications/`.
2. Open the repository in Cursor. Cursor reads `AGENTS.md` and the rules in `.cursor/rules/`; Claude Code reads `CLAUDE.md`; other agents read `AGENTS.md`.
3. In Agent mode, on a new branch, paste: "Read AGENTS.md, then do Step 0 of docs/15-build-plan.md."
4. When the agent finishes, it opens a pull request. Check that the step's "done when" tests pass in CI, review with the checklist in `docs/15` §Working with AI agents and GitHub, merge, then start the next step on a new branch.
5. Run several agents at once only on steps the dependency table in `docs/15` allows, each on its own branch.
6. Give agents the local stack and preview deployments only. Never give an agent production credentials, the Supabase `service_role` key or real personal data.
7. Answer the questions in `docs/16-open-questions.md` as they become relevant.
