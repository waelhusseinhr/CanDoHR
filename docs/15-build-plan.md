# 15 · Build plan for AI coding agents

Build CanDo in the order below. Each step lists what to read, what to build, when it is done, and a prompt to paste into the agent. Do not start a step until the steps it needs have their "done when" checks passing in CI. The agent reads `AGENTS.md` before every step.

Platform: Supabase, Cloudflare Workers, GitHub, AWS KMS and S3 for keys and anchors (`02`). Scope of the first release: steps 0 to 16. Steps 17 to 20 complete the platform.

---

## Working with AI agents and GitHub

### Tools

| Tool | How it gets the rules |
| --- | --- |
| Cursor (Agent mode, any model) | Reads `AGENTS.md` at the root and in subfolders, plus the project rules in `.cursor/rules/` (`00-cando.mdc` always applies; the others attach when the agent edits database, payroll, rules and agreements, test, Workers or web files) |
| Claude Code | Reads `CLAUDE.md`, which points to `AGENTS.md` |
| Other agents (for example Codex) | Read `AGENTS.md` |

`AGENTS.md` is the single source of rules. The Cursor rules and `CLAUDE.md` only point to it and repeat the few rules that matter most for the files being edited.

### Branches and pull requests

- One build step, or one group of stories, per branch: `step-05/core-hr-assignments`. The pull request lists the story IDs and `ENT-` scenarios it completes.
- Agents never push to `main`, never merge, and never change branch protection. `main` requires CI green and one human approval.
- Squash merge. The commit title names the story IDs.
- If an agent believes a protected file is wrong, it opens a separate pull request with the reason and the source, and stops work that depends on it.

### Protected paths (CODEOWNERS)

Changes to these paths need the owner's approval: `rules/`, `tests/`, `reference/`, `schema/`, `api/`, existing files in `supabase/migrations/`, `docs/`, `requirements/`, `AGENTS.md`, `CLAUDE.md`, `.cursor/rules/`, `.github/`, `infra/`. New migration files are allowed and reviewed like code.

### Running several agents at once

Run agents in parallel only on steps that do not depend on each other, each on its own branch (and its own worktree or clone). Never put two agents on the same step.

### Secrets, data and connected tools

- Agents work against the local stack only (`supabase start`, `wrangler dev`) and preview deployments. They never receive staging or production credentials, the Supabase `service_role` key, AWS keys or real personal data.
- If an agent uses MCP servers (Supabase, Cloudflare, GitHub), connect them to local or development projects only, with the Supabase server in read-only mode. Never connect an agent to production.
- Migrations are new files only. An applied migration is never edited. Staging and production migrations run only from GitHub Actions.

### GitHub workflows (created in Step 0)

| Workflow | Trigger | What it does |
| --- | --- | --- |
| `ci.yml` | Every pull request | Type-check, lint, unit and Workers tests, `supabase start` and migrations, schema smoke tests, payroll and agreement fixtures, audit vectors, platform guards (`14` §1), Python reference self-tests, OpenAPI diff, accessibility on changed screens |
| `preview.yml` | Every pull request | Preview Workers deployment and a Supabase preview branch or the shared dev project; Playwright against it |
| `deploy-staging.yml` | Merge to `main` | `supabase db push` to staging, `wrangler deploy --env staging` for every Worker, smoke checks |
| `deploy-production.yml` | Manual, from a tag | Same against production, through the `production` GitHub Environment with the owner as required reviewer |

### The owner's review checklist

- The step's "done when" checks are green in CI.
- No expected value in `tests/` was edited; no statutory value or agreement term appears in code.
- No new way to write business data outside change sets; no table exposed through Supabase's Data API.
- New migrations read sensibly and do not drop or rewrite data.
- No personal data in logs, Queue messages or Durable Object storage.
